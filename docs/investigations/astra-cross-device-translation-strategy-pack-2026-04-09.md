## 一、执行摘要

一句话结论：

> **Astra 现在已经是一个很强的浏览器内翻译产品，但还不是一个“任何设备都能用的翻译助手”。**

当前最强的能力面：

- 网页整页翻译
- YouTube 双语字幕翻译
- 悬停翻译 / 输入框翻译
- PDF / EPUB / 字幕文件翻译

当前最大的不足不在“翻译能力完全不够”，而在以下几层没有真正成立：

- **跨设备覆盖**：主体仍是浏览器扩展，移动端产品形态不完整
- **跨设备连续性**：用户资产仍主要停留在单设备本地
- **浏览器外入口**：还没有形成任意设备、任意内容都能低摩擦使用的入口
- **分发与产品化**：支持矩阵、账号体系、订阅体系、低摩擦安装路径还不够成熟
- **后端承载力**：当前后端更像最小可用 relay / account 服务，而不是完整多设备产品底座

因此，下一阶段最重要的不是继续“横向加很多翻译 feature”，而是先补齐：

1. **跨设备连续性**
2. **通用入口（优先 Web / PWA）**
3. **产品化分发与支持矩阵**

## 二、当前 Astra 的真实现状与边界

### 2.1 现在真正强的地方

Astra 当前最能站得住脚的能力：

- **网页翻译**：整页 / 文章模式、双语 / 仅译文、站点规则、视口优先、动态内容和 SPA 处理都已具备较强能力
- **YouTube 双语字幕翻译**：这是当前最成熟的视频类能力面
- **悬停翻译**：已有独立交互层与验证覆盖
- **输入框翻译**：支持 input / textarea / contenteditable，并有敏感输入规避逻辑
- **PDF / EPUB / 字幕文件 reader**：这些已经不是概念能力，而是有真实产品面和运行时

### 2.2 当前不应夸大的地方

不建议对外过度宣称：

- **已完成移动端产品**：当前 iOS 更接近 Safari Web Extension 宿主壳，Android 基本未形成产品路径
- **图片翻译已成熟可用**：现状不足以支撑这一说法
- **漫画翻译已支持**：当前仍是 gap
- **所有视频平台字幕体验都同等成熟**：目前最能真讲的是 YouTube，其它平台更偏适配层
- **所有数据都只在本地**：账户、配额、usage 元数据在 server，翻译请求也会走 provider / relay

### 2.3 当前的平台边界

- **Chromium 扩展**：事实上的主平台
- **Firefox / Safari 桌面**：更像已具备构建和分发通路，但不是同等成熟度的平台
- **iOS Safari**：本质是 Safari Web Extension 宿主壳与打包骨架
- **Android / 原生桌面 / 原生移动 App / 通用 Web App**：尚未形成完整产品

### 2.4 当前的连续性边界

用户的核心资产仍主要在本地设备：

- 配置
- 词汇本
- 阅读历史
- 学习进度
- 翻译缓存

这意味着 Astra 现在更像：

> **强功能工具**，而不是 **跨设备账户体系产品**。

## 三、Founder / PM 版 1 页战略 memo

## 主题

**Astra 下一阶段不该只做“更强的浏览器翻译扩展”，而要升级成“跨设备翻译助手”。**

## 现状判断

Astra 当前最强的是：

- 网页翻译
- YouTube 字幕翻译
- 悬停 / 输入框翻译
- PDF / EPUB / 字幕文件翻译

这说明 Astra 在**浏览器内翻译体验**上已经具备很强基础。

但如果和用户真正会长期使用的竞品比，Astra 还没有占住更大的用户心智：

> **“无论我在哪个设备上，遇到要翻译的内容，都可以直接用 Astra。”**

现在的 Astra 更像：

- 一个强大的扩展

而不是：

- 一个跨设备翻译产品

## 核心问题

### 1. 平台覆盖不够

- 桌面浏览器是主阵地
- iOS 还是 Safari Web Extension 壳思路
- Android / Web App / 原生 App 还没有形成完整产品路径

### 2. 用户资产不能连续

用户积累的价值还主要留在单设备：

- 词汇
- 配置
- 阅读历史
- 学习进度

这会直接削弱：

- 留存
- 复访
- 付费意愿
- 多设备使用理由

### 3. 浏览器外入口不够多

竞品常见强点是：

- 手机直接翻
- 分享到 App 即翻
- 上传图片 / 文件即翻
- 任意设备打开就能用

Astra 目前仍偏“浏览网页时很强”。

### 4. 分发与产品化不够成熟

用户要形成品牌心智，除了功能，还要有：

- 清晰支持矩阵
- 低摩擦安装路径
- 账号体系
- 订阅体系
- 稳定可信的对外承诺

## 战略判断

Astra 下一阶段最重要的不是再加几个翻译 feature，而是补齐三个基础层：

### A. 跨设备连续性

把这些变成账号级资产：

- 配置同步
- 词汇同步
- 阅读历史同步
- 学习进度同步
- 设备管理

### B. 通用入口

最优先不是双原生，而是：

- **Web / PWA Companion**

这样可以更快实现：

- 任意现代设备可访问
- 文本 / URL / 文件翻译
- 账号 / 词汇 / 历史统一

### C. 产品化分发

把 Astra 从“能用”升级到“普通用户也能稳定获取并长期使用”。

## 建议的优先级

### 先做

1. **桌面端稳定性和支持矩阵**
2. **账号连续性 / 云同步**
3. **Web / PWA Companion**

### 后做

4. iOS 更完整产品化
5. Android 入口
6. OCR / 图片 / 漫画 / 更深系统级能力

## 一句话定位建议

短期不要讲：

- 任何设备都支持
- 移动端已完成
- 全平台一致体验

短期应该讲：

> **Astra 是一个在受支持设备上可连续使用的智能翻译助手。**

等同步 + Web / PWA 成立后，再升级为：

> **Astra 是跨设备翻译助手。**

## 成功标准

如果战略走对，Astra 应该从“浏览器工具”升级为“用户的翻译账户体系”。

核心指标建议：

- 登录用户占比
- 多设备活跃用户占比
- 同步开启率
- 词汇 / 历史跨设备恢复率
- 从桌面到移动入口的转化率
- 付费转化率

## 四、按季度拆解的 roadmap

> 以 2026 年 4 月为起点。

### 2026 年 Q2（4–6 月）

#### 目标

**把 Astra 做成“成熟的桌面翻译产品”。**

#### 重点

1. **桌面支持矩阵收口**
   - 明确 Chrome / Firefox / Desktop Safari 的支持等级
   - 不再模糊宣称“多端都可用”

2. **核心能力 hardening**
   - 网页翻译
   - 悬停翻译
   - 划词 / 输入框翻译
   - 字幕翻译
   - PDF / EPUB / 字幕文件翻译

3. **relay / account 基础设施强化**
   - durable session
   - 更清晰的 quota / usage
   - 更稳定的错误语义
   - 更可信的账号状态

4. **sync-ready 数据模型设计**
   - config
   - vocabulary
   - reading history
   - study progress

#### 本季度输出

- 支持矩阵文档
- 对外 claim 边界
- sync contract
- 更稳定的桌面主产品

#### 本季度不能宣称

- 跨设备同步已完成
- iPhone / Android 已成熟支持
- 任意设备都能用

### 2026 年 Q3（7–9 月）

#### 目标

**把 Astra 做成“可连续使用的账号型产品”。**

#### 重点

1. **云同步最小闭环**
   - config
   - vocabulary
   - reading history

2. **设备管理**
   - 当前设备识别
   - 最近同步状态
   - 设备列表
   - 远程登出 / 撤销

3. **popup / options 升级**
   - 登录状态
   - 同步状态
   - 设备状态
   - 错误恢复入口

4. **数据边界与隐私策略**
   - 哪些默认同步
   - 哪些可选同步
   - 哪些永不上传
   - export / delete / opt-in

#### 本季度输出

- 真正可用的跨浏览器连续性
- “登录后继续你的词汇 / 设置 / 历史”成立

#### 本季度可宣称

> Astra 可在受支持设备上登录并继续你的翻译资产。

### 2026 年 Q4（10–12 月）

#### 目标

**让 Astra 第一次接近“任何设备都能用”。**

#### 重点

1. **上线 Web / PWA Companion**
   - 文本翻译
   - URL 翻译
   - PDF 上传翻译
   - EPUB / 字幕文件导入
   - 词汇 / 历史 / 进度查看
   - 账号与订阅管理

2. **抽共享能力层**
   - types
   - translate client
   - sync contracts
   - vocabulary / reading domain

3. **移动设备先通过 Web 入口承接**
   - 不急于双原生

#### 本季度输出

- 非扩展环境也能用 Astra
- “没有装扩展也能打开 Astra 做翻译”成立

#### 本季度可宣称

> Astra 已支持在受支持浏览器和 Web 入口中连续使用。

### 2027 年 Q1（1–3 月）

#### 目标

**做移动端产品化，而不是只做移动兼容。**

#### 重点

1. **iOS 正式化路线**
   - Safari extension 是否继续主推
   - 是否加入 host app / share extension / deep link

2. **Android 入口定义**
   - Web / PWA + share intent
   - 或轻量原生壳

3. **阅读连续性加强**
   - 最近阅读
   - resume point
   - study progress 恢复
   - 设备间接力

#### 本季度输出

- 明确的移动支持策略
- 第一版真正可运营的移动路径

### 2027 年 Q2 以后

#### 长期方向

- OCR / 图片翻译
- 漫画翻译
- live captions / meeting captions 强化
- 更强隐私模式
- 局部离线 / 本地模型能力
- 统一阅读、翻译、学习工作台

## 五、给团队执行的版本

## 5.1 团队目标

团队接下来 6 周的首要目标，不是“再做更多新翻译 feature”，而是：

> **把 Astra 从强功能扩展，推进为一个有明确支持矩阵、账号连续性前置能力、并为跨设备演进做好协议和数据基础的产品。**

## 5.2 未来 6 周执行重点

### Workstream A：支持矩阵与真实口径收口

#### 目标

把“我们真实支持什么、不支持什么、beta 到什么程度”说清楚。

#### 任务

- 输出支持矩阵文档
- 更新 README / 产品路线图中的平台表述
- 区分 supported / beta / experimental / not supported
- 为 iOS Safari 给出真实验证结论
- 明确哪些能力可以对外 claim，哪些只能内部表述

#### Done when

- 团队内部和对外口径一致
- 不再出现“代码可构建 = 产品已支持”的混淆

---

### Workstream B：账号连续性协议前置

#### 目标

先把云同步和设备体系的 contract 定下来。

#### 任务

- 定义 sync collections
  - config
  - vocabulary
  - reading history
  - study progress
- 定义设备模型
  - device id
  - platform
  - label
  - last seen
- 定义 merge 规则
- 定义同步开关与隐私边界
- 定义 export / delete / opt-in 规则

#### Done when

- 客户端和服务端对同步 contract 有统一理解
- 不需要在 UI 或后端实现时再重新讨论数据模型

---

### Workstream C：relay / account 产品化加固

#### 目标

把当前 server 从“最小可用”提升到“能支撑下一阶段产品”的底座。

#### 任务

- durable session
- 更稳定的 revoke / logout 语义
- 更清晰 quota / usage 语义
- account / entitlement / billing contract 梳理
- 错误码和错误恢复路径梳理

#### Done when

- 登录状态和权限判断更稳定
- 后续 device / sync 能在现有后端上继续生长

---

### Workstream D：桌面核心面稳定性补强

#### 目标

继续巩固最核心的使用场景，避免在跨设备前扩大战线。

#### 任务

- 加强网页翻译、字幕、悬停、输入框、PDF / EPUB / 字幕文件的验证
- 补 deterministic / live / holdout 的关键缺口
- 明确质量 gate
- 统一错误上报与问题分类

#### Done when

- 桌面核心路径成为可放心扩展的基础盘

---

### Workstream E：Web / PWA 方案预研

#### 目标

不立即大规模实现，但要把最短路径选清楚。

#### 任务

- 明确 Web / PWA 的最小功能集
- 识别哪些逻辑可共享，哪些仍绑定 extension
- 定义 shared translate client / sync transport / settings/session adapter 的抽象边界
- 决定目录与工程策略（独立 app vs 继续塞进 extension entrypoints）

#### Done when

- 团队能在下一季度直接启动 Web / PWA，而不是再做一轮方向争论

## 5.5 团队版风险提醒

需要避免的几个典型错误：

1. **过早做双原生**
   - 在账号连续性和 Web 入口未成立前，直接投入双原生会显著分散资源

2. **继续横向扩太多新 feature**
   - 在基础盘未收口前继续铺新面，会让质量和支持矩阵更混乱

3. **把“可构建”误当成“可承诺”**
   - 这是当前最容易伤害对外可信度的问题

4. **先做 UI，后补协议**
   - sync / device / privacy contract 必须先定，否则返工会很重

## 六、给投资人的版本

## 6.1 投资叙事一句话

> **Astra 正在从一个高质量浏览器翻译工具，升级为一个跨设备的语言理解与翻译入口。**

## 6.2 Astra 已经证明了什么

Astra 不是一个还停留在想法阶段的产品。它已经在浏览器内证明了：

- 用户真实会遇到的阅读 / 字幕 / 输入场景是可以被高质量 AI 翻译重构的
- 不同内容面可以共享一套翻译与策略中枢
- 翻译并不只是一次性工具行为，而可以沉淀成长期学习资产

换句话说，Astra 已经验证了：

> **“翻译 + 理解 + 学习积累”可以成为一个真实产品，而不只是模型调用包装。**

## 6.3 下一阶段为什么成立

今天的机会不只是做“另一个翻译工具”，而是做：

- 用户在不同设备上持续依赖的翻译账户体系
- 能承接网页、文档、字幕、文本与未来更多输入面的统一入口
- 从即时翻译走向长期积累和复用的语言工具

这意味着 Astra 的成长逻辑不是单点 feature 竞争，而是：

1. **先赢下高频刚需入口**
2. **再沉淀用户资产**
3. **最后形成跨设备连续性和更高留存**

## 6.4 为什么现在的重点不是“再多几个 feature”

如果今天继续横向加很多新能力，Astra 当然会看起来更丰富；
但真正决定它能否变成更大产品的，是三件更基础的事：

- 账号连续性
- 通用入口（Web / PWA）
- 产品化分发和支持矩阵

这三件事一旦成立，Astra 的产品形态就会从：

- “一个浏览器插件”

变成：

- “一个用户可长期依赖的跨设备翻译助手”

## 6.5 投资人最该关注的里程碑

### 里程碑 1：桌面产品成熟化
信号：
- 支持矩阵收口
- 核心路径稳定
- 对外承诺更可信

### 里程碑 2：账号型产品成立
信号：
- 设置 / 词汇 / 历史可跨设备恢复
- 多设备活跃用户开始出现
- 产品不再依赖单设备偶发使用

### 里程碑 3：Web / PWA Companion 上线
信号：
- 没装扩展也能进入 Astra 生态
- Astra 从扩展产品升级为跨设备入口

### 里程碑 4：移动端路径跑通
信号：
- iPhone / Android 有真实可运营入口
- 设备覆盖开始变成增长驱动，而不仅是技术兼容

## 6.6 对外应该怎么讲

当前阶段更适合的对外表述：

> Astra 正在构建一个从浏览器切入、逐步扩展到跨设备的智能翻译助手。

比起直接说“全平台已支持”，更稳妥也更有说服力。

## 6.7 投资人版核心判断

Astra 的价值不只是“翻译做得不错”，而是它已经拥有一条清晰的产品升级路径：

- 从浏览器高频使用场景切入
- 沉淀用户词汇与阅读资产
- 扩成跨设备连续使用的账户体系
- 最终进入更广的语言理解与学习市场

这条路径如果走通，Astra 的护城河将不只来自模型效果，而来自：

- 使用频率
- 用户资产积累
- 跨设备连续性
- 更低摩擦的入口占领

## 七、最后的压缩建议

如果当前只抓最关键的 3 件事：

### P1
